Everything so far has used plain HTML, and that is deliberate. HTML elements come with roles, names, states and keyboard behaviour built in. But sometimes HTML runs out. There is no native element for a toggle button's pressed state, for a set of tabs, or for "say this out loud when the basket changes". That is where **ARIA** (Accessible Rich Internet Applications) comes in: a set of attributes that let you describe roles, states and relationships directly to the accessibility tree.

## The first rule of ARIA

The W3C's own guidance starts with a rule that surprises people: **if you can use a native HTML element with the behaviour you need, do that instead of ARIA.** WebAIM's annual scans of the top million home pages keep finding that pages using ARIA have more detected errors, not fewer. The reason is simple. ARIA only changes what is **announced**. It doesn't make anything focusable, doesn't add keyboard handling, and doesn't change appearance. Every ARIA attribute is a promise to assistive technology that your JavaScript then has to keep.

```html
<!-- A promise with nothing behind it -->
<span role="button">Add to basket</span>

<!-- The same promise, kept by the browser -->
<button type="button">Add to basket</button>
```

## Roles, properties and states

ARIA attributes fall into three groups.

**Roles** say what something is: `role="tab"`, `role="dialog"`, `role="switch"`, `role="status"`. You rarely need them for things HTML already has.

**Properties** describe relationships or fixed characteristics: `aria-labelledby` and `aria-describedby` (you used both on forms), `aria-controls`, `aria-required`, `aria-haspopup`.

**States** describe things that change as the user interacts, and your script must update them: `aria-expanded`, `aria-pressed`, `aria-checked`, `aria-selected`, `aria-current`, `aria-disabled`, `aria-invalid`.

Ticketly's wishlist heart is a good example. It is already a real button, but nothing tells a screen reader whether the event is saved. `aria-pressed` turns it into a toggle button:

```html
<button type="button" class="fav" aria-pressed="false">Save to wishlist</button>
```

```js title=ticketly/wishlist.js
fav.addEventListener('click', () => {
  const saved = fav.getAttribute('aria-pressed') === 'true';
  fav.setAttribute('aria-pressed', String(!saved));
});
```

NVDA now says "Save to wishlist, toggle button, not pressed", then "pressed" after activation. Notice that the label stays the same; the state carries the change. And you can style from the state directly, which keeps the visuals and the semantics from drifting apart:

```css
.fav[aria-pressed='true'] {
  background: #5b3cc4;
  color: #fff;
}
```

For the current page in a navigation menu, `aria-current="page"` tells screen reader users which link they are on: "Tickets, current page, link".

:::mistake aria-hidden on something focusable
A developer saw the "Add to basket" button announced twice (once in the card, once in a sticky bar) and added `aria-hidden="true"` to one of them. The button is still in the tab order, so keyboard users land on it, and the screen reader says nothing because it is hidden from the tree. Never hide focusable elements. If something truly is a duplicate, remove it, or make it `inert`.
:::

A few more rules from the W3C's "Using ARIA" note keep you out of trouble:

- Don't change native semantics unless you really must: `<h2 role="button">` destroys the heading. Put a button inside the heading instead.
- Every interactive ARIA control must be keyboard operable.
- Every interactive element needs an accessible name.

## Live regions: announcing changes

When Ticketly adds a ticket, the basket counter in the header changes from 1 to 2. Sighted users notice. Screen reader users hear nothing, because their focus is still on the button they pressed. A **live region** is an element whose content changes are read out automatically, without moving focus.

```html title=ticketly/index.html
<p id="basket-status" role="status"></p>
```

```js
function addToBasket() {
  count += 1;
  basketStatus.textContent = `Ticket added. ${count} tickets in your basket.`;
}
```

Three rules make live regions reliable:

1. **The region must exist before the change.** Screen readers watch existing live regions for changes. Inserting a new element that already contains text is often missed. Render the empty region at page load.
2. **Pick the politeness.** `role="status"` (same as `aria-live="polite"`) waits until the screen reader finishes its current sentence. `role="alert"` (assertive) interrupts. Reserve alerts for urgent, rare messages like a failed payment; an assertive "Ticket added" on every click is exhausting.
3. **Keep messages short and meaningful.** Announce the result ("2 tickets in your basket"), not the mechanics ("basket component updated").

:::tip When to move focus instead
Live regions are for status updates while the user carries on. If the user must act on the new content, as with a dialog or the error in a form field, move focus to it instead. Moving focus and announcing the same message would make the screen reader say it twice.
:::
