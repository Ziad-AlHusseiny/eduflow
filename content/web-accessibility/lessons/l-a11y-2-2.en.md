Ticketly's "Add to basket" control looks like a button: rounded corners, a brand colour, a pointer cursor on hover. It is a `div` with an `onclick`. Click it with a mouse and it works perfectly, which is exactly why nobody on the original team noticed. Press Tab and focus jumps straight past it. Samir's screen reader reads it as plain text. A switch user can't reach it at all.

## Links go, buttons do

The decision between the two native controls comes down to one question: **does it take the user somewhere?**

- A **link** (`<a href="…">`) navigates: to another page, another part of this page (`#lineup`), a file, an email address. Screen readers announce it as "link". Users expect to open it in a new tab, copy its address, see it in history. It activates with **Enter**.
- A **button** (`<button>`) performs an action on the current page: add to basket, open a dialog, submit a form, toggle a filter. Screen readers announce it as "button". It activates with **Enter and Space**.

Styling is irrelevant to the choice. A link can look like a big call-to-action and a button can look like a text link; CSS handles appearance, the element handles behaviour.

## What the clickable div is missing

To understand why the native element wins, count what a `div` lacks. Here is the minimum to rebuild a button by hand:

```html
<div class="btn" role="button" tabindex="0">Add to basket</div>
```

```js
const fake = document.querySelector('.btn');
fake.addEventListener('click', addToBasket);
fake.addEventListener('keydown', (event) => {
  if (event.key === 'Enter') addToBasket();
  if (event.key === ' ') event.preventDefault(); // stop the page scrolling
});
fake.addEventListener('keyup', (event) => {
  if (event.key === ' ') addToBasket(); // native buttons fire on Space release
});
```

That is a role, focus, Enter, Space and scroll prevention, and it still lacks a disabled state, form submission, and the way Windows contrast themes (forced colors mode) style buttons. Compare:

```html
<button type="button" class="btn" onclick="addToBasket()">Add to basket</button>
```

One element, and every behaviour is correct in every browser and every screen reader. This is the pattern you will see throughout the course: **native HTML first**, because the browser has already done the hard work.

:::mistake The href="#" action link
`<a href="#" onclick="removeItem()">Remove</a>` is focusable and works with Enter, so it looks fixed. But it is announced as a link, doesn't respond to Space, and if the script fails it jumps to the top of the page and adds a history entry. An `<a>` without any `href` is worse: it isn't even focusable. If it acts, make it a button.
:::

## Buttons in forms, and disabled buttons

Inside a `<form>`, a `<button>` defaults to `type="submit"`. Ticketly's checkout has an "Apply promo code" button that kept submitting the whole form. The fix is one attribute:

```html
<button type="button" onclick="applyPromo()">Apply promo code</button>
```

The `disabled` attribute removes a button from the tab order, so keyboard users tabbing through the form skip straight past it, and nobody is told why it is unavailable. A screen reader in browse mode still finds it, announced as "unavailable", but with no reason attached. For a "Pay now" button that is waiting on a valid card, consider leaving it enabled and explaining the problem when it is pressed, which you will build in [Accessible Forms](lesson:l-a11y-2-3).

## Text that makes sense alone

Screen reader users often pull up a list of all links or buttons on a page, and voice control users say the visible text to click it. "Read more", "Click here" and "Details" are meaningless in that list. WCAG 2.4.4 asks that a link's purpose be clear from its text, or its text plus its surrounding sentence or list item. Aim higher than the minimum: write "Friday line-up and set times", not "Read more". If the design insists on short visible text, you will learn in [Accessible Names and Descriptions](lesson:l-a11y-4-3) how to extend the name without breaking voice control.

One more link habit: if a link opens a new tab or downloads a file, say so in its text, for example "Venue guide (PDF, 2 MB)" or "Seating plan (opens in a new tab)". An unexpected new tab breaks the Back button for screen reader and magnifier users, who often don't notice that the window changed and wonder why they can't return.

:::tip The quick keyboard test
Unplug your mouse (or ignore it) and press Tab through Ticketly. Every control you can click must receive focus, show where focus is, and respond to Enter, plus Space for buttons. Anything that fails is almost always a div, a span, or a link without an href.
:::

Real buttons and links fix the controls that act. Next come the controls that collect information, and the place where most inaccessible sites lose their customers: forms.
