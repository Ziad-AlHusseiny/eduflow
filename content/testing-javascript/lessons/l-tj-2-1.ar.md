لمجموعة الاختبارات مهمّتان: **أن تفشل حين ينكسر السلوك**، و**أن تبقى خضراء حين لا ينكسر**. معظم الفرق تركّز على الأولى وتنسى الثانية. ثم يعيد أحدهم تسمية دالة خاصة، فيتحوّل أربعون اختبارًا إلى الأحمر، دون أن يتغيّر أي سلوك، والدرس الذي يتعلّمه الفريق هو "الاختبارات تبطّئنا".

## السلوك مقابل التفاصيل الداخلية

إليك `splitEvenly` في Splitwise-lite، التي تقسّم فاتورة بالسنتات بين الأشخاص. تذهب السنتات المتبقّية إلى أوائل الأشخاص في القائمة، فتكون النتيجة عادلة (لا تختلف الحصص بأكثر من سنت واحد) وحتمية:

```js run
function splitEvenly(totalCents, people) {
  if (!Number.isInteger(people) || people < 1) {
    throw new RangeError('people must be a positive integer');
  }
  const base = Math.floor(totalCents / people);
  const remainder = totalCents % people;
  return Array.from({ length: people }, (_, i) => (i < remainder ? base + 1 : base));
}

console.log(splitEvenly(1000, 3)); // $10.00 three ways
console.log(splitEvenly(1001, 4));
console.log(splitEvenly(2, 3));
```

**سلوكها** هو كل ما يستطيع المستدعي ملاحظته: المصفوفة التي تعيدها، والخطأ الذي ترميه حين يكون عدد الأشخاص صفرًا. أما **تفاصيلها الداخلية** فهي الطريقة: `Math.floor`، والعامل `%`، و`Array.from`، وأسماء المتغيّرات. تستطيع إعادة كتابة جسم الدالة بحلقة، أو بتوزيع السنتات واحدًا تلو الآخر، دون أن يلاحظ أيّ مستدعٍ شيئًا.

الاختبار الذي يفحص السلوك يصمد أمام كل إعادات الكتابة هذه. أما الاختبار الذي يفحص التفاصيل الداخلية فينكسر مع كل واحدة منها، رغم أن شيئًا مما يهمّ المستخدم لم يتغيّر. هذا *إنذار كاذب*، والإنذارات الكاذبة مكلفة: كل واحد منها يكلّف جلسة تتبّع أخطاء، وتراكمها يعلّم الناس إعادة تشغيل الاختبارات الحمراء أو حذفها دون قراءتها.

## كيف تبدو الاختبارات المرتبطة بالتفاصيل الداخلية

هذه أنماط حقيقية حذفتها بنفسي من قواعد كود:

```js
// Spying on Math.floor: breaks if you switch to integer division another way
const floor = vi.spyOn(Math, 'floor');
splitEvenly(1000, 3);
expect(floor).toHaveBeenCalledWith(1000 / 3);

// Testing an exported private helper: breaks when you inline or rename it
expect(_remainderFor(1000, 3)).toBe(1);

// Snapshotting the source-shaped output of a debug helper nobody calls
expect(describeSplit(1000, 3)).toMatchSnapshot();
```

كل واحد منها ينجح اليوم ولا يخبرك بشيء لا يخبرك به اختبار السلوك. وكل واحد منها سيفشل في اليوم الذي يحسّن فيه أحدهم الكود.

## اختبار العقد بدلًا من ذلك

ابدأ مما يعتمد عليه المستدعي. بالنسبة إلى `splitEvenly` فهو:

1. حصة واحدة لكل شخص.
2. **مجموع الحصص يساوي الإجمالي.** لا يضيع سنت، ولا يُختلَق سنت.
3. لا تختلف الحصص بأكثر من سنت واحد.
4. تذهب السنتات الإضافية إلى أوائل الأشخاص (وهذا موثّق، فقد يعتمد عليه المستدعون).
5. عدد الأشخاص صفر خطأ.

النقطتان 2 و3 *ثوابت* (invariants): تصحّ مع كل مدخل صالح، لذا تستطيع فحصها على عدة مدخلات دفعة واحدة:

```js title=src/split.test.js
import { describe, test, expect } from 'vitest';
import { splitEvenly } from './split.js';

const sum = (xs) => xs.reduce((a, b) => a + b, 0);

describe('splitEvenly', () => {
  test('never loses or invents a cent', () => {
    for (const [total, people] of [[1000, 3], [1001, 4], [2, 3], [0, 5]]) {
      expect(sum(splitEvenly(total, people))).toBe(total);
    }
  });

  test('gives the leftover cents to the first people', () => {
    expect(splitEvenly(1001, 4)).toEqual([251, 250, 250, 250]);
  });

  test('refuses to split between zero people', () => {
    expect(() => splitEvenly(1000, 0)).toThrow(RangeError);
  });
});
```

ثابت المجموع هو أثمن سطر في الملف. النسخة التي تُسقط الباقي تفشل فيه. وكذلك الخطأ بفارق واحد (off-by-one) الذي يوزّع سنتًا زائدًا. لا يهمّه كيف تُحسب الحصص، بل يهمّه فقط أن المال محفوظ.

:::mistake تصدير الأجزاء الداخلية لاختبارها
إن شعرت أن دالة مساعدة مهمّة بما يكفي لتُختبر وحدها، فاسأل: أيّ سلوك عام يعتمد عليها؟ ثم اختبر ذلك السلوك بمدخل يشغّل الدالة المساعدة. وإن كانت الدالة المساعدة فعلًا مفهومًا مستقلًّا يُستخدم في عدة أماكن، فارفعها إلى وحدة برمجية حقيقية لها عقدها الخاص. أما "مُصدَّرة من أجل الاختبارات فقط" فهي أسوأ الحالين: عامة، لكن دون أي وعود.
:::

## ما مدى الدقّة المطلوبة في الـ assertions؟

يمكن لاختبارات السلوك أن تبقى دقيقة. `toEqual([251, 250, 250, 250])` يثبّت الترتيب الموثّق للسنتات الإضافية، وهذا سلوك لأن المستدعين يعتمدون عليه. السؤال ليس أبدًا "دقيق أم مرن؟" بل "هل سيلاحظ مستخدم أو مستدعٍ لو تغيّر هذا؟" إن كانت الإجابة نعم، فأكّده بدقّة. وإن كانت لا، فلا تؤكّده أصلًا.

## حين تكسر إعادة الهيكلة اختبارًا فعلًا

أحيانًا *يجب* أن يغيّر تعديل الكود اختبارًا ما، ومن المفيد أن تعرف في أيّ حالة أنت. إن تغيّر العقد العام (صارت الدالة تعيد كائنات بدل أرقام، أو صارت السنتات الإضافية تذهب إلى الدافع)، فالاختبار محقّ في فشله، وتحدّثه عن قصد، ويُفضَّل أن يكون ذلك قبل تغيير الكود. أما إن بقي العقد كما هو وفشل اختبار رغم ذلك، فقد كان الاختبار مرتبطًا بالتفاصيل الداخلية: أعد كتابته على أساس العقد واحذف القديم. المجموعة السليمة تجعل الإجابة عن هذا السؤال سهلة، لأن اسم كل اختبار يذكر وعدًا يقطعه الكود.

في التمرين، اكتب اختبارات سلوك لـ `splitEvenly` تلتقط أربعة أخطاء واقعية. والدرس القادم عن إيجاد المدخلات التي تكشف أخطاءً كهذه.
