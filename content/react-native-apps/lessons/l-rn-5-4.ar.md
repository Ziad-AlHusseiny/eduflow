تُبلغ مستخدمة أن Trailhead يرفض "8,4" مسافةً على هاتفها الألماني. تصلح أداة التحليل في خمس دقائق. ودون أي شيء آخر، يعني إيصال هذا الإصلاح إليها build جديدًا، وإرسالًا، ومراجعة، ثم انتظار أن تحدّث تطبيقها. يختصر **EAS Update** ذلك إلى أمر واحد: ينشر كود JavaScript وassets جديدة، وتنزّلها نسخ Trailhead المثبّتة في المرة التالية التي تبدأ فيها.

## كيف يصل التحديث إلى الهاتف

يحتوي build الإصدار على شيئين: التطبيق الأصلي (كود Swift وKotlin وC++ المترجَم، بما في ذلك كل وحدة أصلية)، و**حزمة JavaScript مضمّنة**. والتحديث يستبدل الجزء الثاني فقط. حين يبدأ التطبيق، يتحقّق `expo-updates` من الخادم بحثًا عن حزمة أحدث لقناته وإصدار وقت التشغيل الخاص به. وافتراضيًا، يبدأ فورًا بالكود الذي لديه أصلًا، وينزّل التحديث الجديد في الخلفية، ويستخدمه في التشغيل **التالي**. لا ينتظر بدء التشغيل الشبكةَ أبدًا، وهذا مهم لتطبيق يُفتح عند بداية درب وفيه خطّ إشارة واحد.

اضبطه مرة واحدة، ثم اصنع builds جديدة لتتضمّن إعدادات التحديث:

```bash
eas update:configure
```

هذا يضيف رابط التحديث و`runtimeVersion` إلى إعدادات تطبيقك. ثم أعطِ كل build profile قناة (channel) في `eas.json`:

```json title=eas.json
{
  "build": {
    "preview": { "distribution": "internal", "channel": "preview" },
    "production": { "autoIncrement": true, "channel": "production" }
  }
}
```

ونشر تحديث أمر واحد:

```bash
eas update --channel production --message "Accept comma decimals in distance"
```

تلتقطه الـ production builds في تشغيلها التالي. انشر على `preview` أولًا، وتحقّق منه على builds المختبِرين، ثم انشر الكود نفسه على `production`.

## ما يمكن أن يصل عبر الهواء وما لا يمكن

| يصل باستخدام `eas update` | يحتاج إلى build جديد وإصدار في المتجر |
|---|---|
| الـ components والشاشات والتنسيقات والمنطق | إضافة وحدة أصلية أو ترقيتها |
| الصور والخطوط المضمّنة مع JavaScript | أوصاف الأذونات وغيرها من الإعدادات الأصلية |
| إصلاح الأخطاء وتعديل النصوص | أيقونة التطبيق وشاشة البداية ومعرّف الحزمة |
| شاشات جديدة مبنية من وحدات أصلية موجودة | ترقيات Expo SDK |

هذا هو التمييز بين JavaScript والكود الأصلي من الدرس الثاني في الدورة، وقد صارت له عواقب الآن. إن مسّ تغيير ما الكود الأصلي أو الإعدادات الأصلية، فلا يستطيع التحديث إيصاله.

## إصدارات وقت التشغيل تُبقي التحديثات متوافقة

تخيّل أن Trailhead 1.1 يضيف `expo-camera`. كود JavaScript الخاص به يستورد وحدة أصلية لا تحتويها builds الإصدار 1.0. لو تلقّى مستخدمو 1.0 ذلك التحديث، لانهار التطبيق حين يلمس الكاميرا. يمنع **إصدار وقت التشغيل** (runtime version) ذلك: كل build وكل تحديث يحمل واحدًا، ولا ينطبق التحديث إلا على الـ builds التي لها إصدار وقت التشغيل نفسه.

```json title=app.json
{
  "expo": {
    "version": "1.1.0",
    "runtimeVersion": { "policy": "appVersion" }
  }
}
```

مع سياسة `appVersion`، يكون إصدار وقت التشغيل هو `version` الخاص بتطبيقك، فترفع `version` كلما تغيّر الكود الأصلي، فتتوقّف builds الإصدارين 1.0 و1.1 عن مشاركة التحديثات. أما سياسة `fingerprint` فتحسب hash للأجزاء الأصلية من مشروعك بدلًا من ذلك، فيتغيّر إصدار وقت التشغيل تلقائيًا حين يتغيّر الكود الأصلي. كلتاهما تعمل؛ اختر واحدة وافهمها.

:::mistake إطلاق تغييرات أصلية بوصفها تحديثًا
العطل الكلاسيكي: يضيف مطوّر مكتبة أصلية، ويختبر في development build جديد حيث تعمل، وينشر تحديثًا دون إصدار وقت تشغيل جديد. تتلقّى الـ builds الأقدم كود JavaScript يستدعي وحدة لا تملكها. قبل كل `eas update`، اطرح سؤالًا واحدًا: هل تغيّر أي شيء أصلي منذ الـ build الذي تخدمه هذه القناة؟ إن كانت الإجابة نعم، فهو build جديد وإصدار في المتجر.
:::

## حين يسوء تحديث

تصل التحديثات إلى مستخدمين كثيرين بسرعة، وهذا سلاح ذو حدّين. إن أساء أحدها التصرّف، فتراجع:

```bash
eas update:rollback
```

يرشدك خطوة بخطوة لإعادة فرع القناة إلى تحديث سابق أو إلى الكود المضمّن في الـ build. ويحصل المستخدمون على التراجع في تشغيلهم التالي، بالطريقة نفسها التي حصلوا بها على التحديث. ولهذا يستحق كل تحديث العناية نفسها التي يستحقها الإصدار: شغّل اختباراتك، وانشر على `preview`، وافتحه على هاتف حقيقي، ثم انشر على `production`. يسمح المتجران بتحديث JavaScript بهذه الطريقة لإصلاح الأخطاء والتحسينات؛ أما استخدامه لتغيير ما يفعله التطبيق جوهريًا دون مراجعة فمخالف لقواعدهما.

## روتين إصدار يصمد

هذا إيقاع يناسب فريقًا صغيرًا:

- **إصلاحات JavaScript**: اختبر، ثم `eas update` إلى preview، وتحقّق، ثم إلى production. في اليوم نفسه.
- **التغييرات الأصلية أو الميزات الجديدة**: ارفع `version`، ثم production build، ثم TestFlight والمسار الداخلي، ثم المراجعة، ثم الإطلاق. بتخطيط مسبق، كل بضعة أسابيع.
- **مع كل إصدار**: راقب تقارير الانهيار في اليوم الأول، وأبقِ `eas update:rollback` جاهزًا.

## أين وصلت الآن

بدأت بـ `Text` واحد في مشروع Expo. أما Trailhead الآن ففيه قوائم تبقى سريعة، وtabs وstacks مع params مضبوطة الأنواع، ونموذج يتعامل مع لوحة المفاتيح، وبيانات في SQLite وtoken في التخزين الآمن، وتتبّع GPS، وصور، وتذكيرات، واختبارات، وbuilds للمتاجر، وطريقة لإصلاح الأخطاء في عصر اليوم نفسه. والأهم أنك تعرف أين يختلف React Native عن الويب ولماذا: native views، وthreads اثنان، ولا cascade، وأذونات يمكن رفضها، ونوعان من التغييرات، JavaScript وأصلي.

خطوات تالية جيدة: أضف Reanimated وreact-native-gesture-handler لتفاعلات أغنى، وTanStack Query لبيانات الخادم، وMaestro لبضعة اختبارات end-to-end. ثم أطلق شيئًا صغيرًا لمستخدمين حقيقيين وتعلّم مما يفعلونه به.
