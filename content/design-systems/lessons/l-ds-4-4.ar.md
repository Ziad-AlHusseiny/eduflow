## الـ stories حالات اختبار

الـ story في Storybook تعرض مكوّنًا في حالة واحدة بـ props محدّدة. كتبت stories للتوثيق في القسم السابق؛ والـ stories نفسها هي العمود الفقري للاختبار:

- **العرض:** يجب أن تُعرض كل story دون أخطاء.
- **التفاعل:** يمكن أن تحمل الـ story دالة `play` تنقر وتكتب وتتحقّق، مثل «الضغط على Escape يغلق الـ Dialog ويعيد التركيز إلى الـ trigger».
- **إمكانية الوصول:** إضافة إمكانية الوصول (accessibility addon) تشغّل فحوص axe-core على كل story وتبلّغ عن المخالفات مثل التسميات الناقصة أو التباين الفاشل.
- **البصري:** تُلتقط صورة لكل story وتُقارن بصورة مرجعية معتمدة.

تستطيع إصدارات Storybook الحديثة تشغيل الـ stories كاختبارات عبر تكامل مع Vitest ‏(`@storybook/addon-vitest`)، فتعمل الملفات نفسها في واجهة Storybook وفي الطرفية وفي الـ CI. وتشترط Northwind story واحدة لكل خانة في مصفوفة الحالات من درس إمكانية الوصول. هذه القاعدة تمنحك تغطية اختبارية شبه مجانية، لأن عمل تصميم الحالات أُنجز أصلًا.

## اختبار الانحدار البصري

اختبار الانحدار البصري يعرض story، ويلتقط صورة، ويقارنها بكسلًا بكسلًا بصورة مرجعية محفوظة. وإن اختلفتا بما يتجاوز حدًّا معيّنًا، يفشل الاختبار ويعرض الفرق. ثم يقرّر إنسان: إن كان التغيير مقصودًا، يقبله صورةً مرجعية جديدة؛ وإن لم يكن، يصلح الكود.

تختار الفرق عادةً أحد إعدادين. خدمة مستضافة مثل Chromatic، التي يصنعها القائمون على Storybook، تعرض الـ stories في السحابة وتعطي المراجعين واجهة ويب لقبول الفروقات. أو تلتقط الصور بنفسك باستخدام Playwright:

```ts title=tests/visual.spec.ts
import { test, expect } from '@playwright/test';

const stories = ['components-button--primary', 'components-button--danger', 'components-dialog--confirm'];
const themes = ['light', 'dark'];
const densities = ['comfortable', 'compact'];

for (const id of stories) {
  for (const theme of themes) {
    for (const density of densities) {
      test(`${id} ${theme} ${density}`, async ({ page }) => {
        await page.goto(`/iframe.html?id=${id}&viewMode=story`);
        await page.evaluate(([t, d]) => {
          document.documentElement.dataset.theme = t;
          document.documentElement.dataset.density = d;
        }, [theme, density]);
        await expect(page).toHaveScreenshot(`${id}-${theme}-${density}.png`);
      });
    }
  }
}
```

كل story تُعرض في كل تركيبة من الـ theme والكثافة، ومعهما العلامة في مجموعة Northwind الحقيقية، وهكذا كان سيُلتقط انحدار ارتفاع السطر. والدالة `toHaveScreenshot` في Playwright تعطّل حركات CSS افتراضيًا وتعيد المحاولة حتى تتطابق لقطتان متتاليتان، فتزيل أشيع مصادر الضجيج.

:::mistake صور مرجعية من أجهزة مختلفة
الخطوط وتنعيم الحواف تختلف بين macOS وWindows وLinux، فالصورة المرجعية الملتقطة على حاسوب محمول لن تطابق لقطة مأخوذة في الـ CI. ولّد الصور المرجعية وقارنها في بيئة واحدة ثابتة، وعادةً حاوية الـ CI، واترك المطوّرين يحدّثونها عبر الـ CI لا محليًا.
:::

والاختبارات البصرية تحرس طبقات الـ tokens أيضًا. تضيف Northwind قاعدة Stylelint في مهمّة الـ CI نفسها ترفض أي إشارة إلى primitive token، مثل `var(--nw-blue-600)`، داخل أنماط المكوّنات. ثم تؤكّد المجموعة البصرية أن الـ CSS الملتزم بالقاعدة ما زال يعرض ما اعتمده المصمّمون.

## خط الإصدار

الاختبار لا يحمي المستخدمين إلا إذا كان النشر عاجزًا عن تخطّيه. لخط الإصدار في Northwind نصفان.

**على كل pull request:** التثبيت بـ `npm ci`، وتشغيل فحوص الـ tokens (التسمية، والمراجع، والتباين)، وفحص الأنواع، والـ lint، واختبارات الوحدات والـ stories، وفحوص إمكانية الوصول، والاختبارات البصرية، واشتراط ملف changeset حين تتغيّر حزمة. ولا يمكن دمج الـ pull request حتى تنجح كل هذه، ويوافق عضو من النواة على الفروقات البصرية.

**على main:** يجمع إجراء Changesets الـ changesets المعلّقة في pull request باسم «Version Packages» يرفع الإصدارات ويحدّث `CHANGELOG.md`. ودمج هذا الـ pull request يشغّل خطوة النشر:

```yaml title=.github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write        # push version commits and tags
      pull-requests: write   # open the Version Packages pull request
      id-token: write        # npm trusted publishing
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run build
      - run: npm test
      - uses: changesets/action@v2
        with:
          publish-script: npm run release
```

النشر يحدث أخيرًا، ومن `main` وحده، وبعد البناء والاختبارات فقط. وبعد خروج الحزم، ينشر سير العمل نفسه موقع التوثيق ونسخة Storybook، ويستورد فريق النواة الـ tokens التي صدرت في الإصدار إلى مكتبة Figma.

:::tip الإصدارات التجريبية للتغييرات الخطرة
للإصدار الـ major، انشر إصدارات تجريبية (prereleases) مثل `5.0.0-next.1` تحت dist-tag منفصل في npm، حتى لا يلتقطها `npm install` افتراضيًا. فريقان أو ثلاثة متطوّعون يثبّتونها قبل بضعة أسابيع، فيجدون مشكلات الانتقال التي فاتت الـ codemods.
:::

في التمرين تراجع سير عمل للإصدار يمكنه نشر كود معطوب. وبهذا يكتمل قسم التسليم؛ وبعده توسّع النظام ليخدم أربعين فريقًا.
